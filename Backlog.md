# Backlog

Documento interno para registrar ideas, decisiones y pendientes de futuras implementaciones.

- Estado: activo
- Apertura: 2026-04-11
- Ultima actualizacion: 2026-05-15
- Visibilidad: interno, no enlazar desde el sitio
- SEO: excluir de enlaces publicos, `sitemap.xml` y rastreo por `robots.txt`

## Decision operativa vigente

- 2026-05-15: la operacion interna migra de Meta WhatsApp Cloud API a Telegram Bot API. `POST /api/telegram/webhook` valida `X-Telegram-Bot-Api-Secret-Token`, grupo operativo, operador autorizado y payload HMAC compacto antes de ejecutar `pending_transfer -> paid|expired`, `paid -> delivering` o `delivering -> delivered`. WhatsApp queda conservado solo como canal publico de soporte al cliente.
- 2026-05-05: el flujo vigente ya usa deploy persistente por GitHub Actions/Cloudflare, Resend como canal principal de emails, numero visible `DDMMRRR` unico en `Ventas.order_number` y panel operativo manual para estados `pending_transfer -> paid/expired -> delivering -> delivered`.
- 2026-05-02: el checkout queda documentado como flujo de 2 pasos (`Pedido` y `Datos`) con cierre activo por `Transferencia Bancaria`. `POST /api/checkout-orders` crea el pedido, lo deja en `pending_transfer` y muestra los datos BCI para pago manual. Flow queda como flujo legado/desactivado por defecto con `flow_enabled=false`.
- 2026-04-30: decision historica ya superada por el cierre de transferencia del 2026-05-01. Mientras Flow se demoraba, el cierre activo del pedido web paso a `Email + WhatsApp`: el cliente armaba el pedido, confirmaba total y datos, el Worker registraba el pedido y enviaba un evento completo a `contacto@caferoast.cl`, y el navegador terminaba en WhatsApp.

## Avances incorporados al 2026-05-05

- El `Worker` quedo desplegable por GitHub Actions y ya fue publicado manualmente con Cloudflare Wrangler, evitando depender de variables locales efimeras.
- Resend quedo como canal activo de email cliente y operativo; Apps Script queda como legado/documentacion, no como dependencia principal para nuevos pedidos.
- La confirmacion de pedido usa numero visible de 7 digitos `DDMMRRR`, persistido y reutilizado entre emails, paginas publicas y cambios de estado.
- El panel operativo ya permite acciones manuales de transferencia, expiracion, despacho y entrega; falta validar el ciclo completo en produccion con un pedido `NO PREPARAR`.
- Telegram operativo ya existe en codigo y health-check; falta cargar secretos productivos, configurar el webhook del bot y ejecutar una prueba real.
- Existe el workflow manual `Telegram E2E Production` para validar en produccion `/api/health`, callbacks Telegram firmados, seguridad negativa, transferencia completa, expiracion y Flow real opcional con pago humano.
